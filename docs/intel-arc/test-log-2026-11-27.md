### NPU 本次实际过程

- 23:07 开始，24 个 60 s chunk；
- chunk 1–14 正常，约 6.0x（`9.2–10.6 s` / 60 s）；
- **23:10:20 在 chunk 15/24 发生 `DEVICE_LOST`**：

```

ZE_RESULT_ERROR_DEVICE_LOST, code 0x70000001
- device hung, reset, was removed, or driver update occurred
```

- 按设计回退 **Intel CPU**（不回退核显），CPU 从 0 重新转录完整 1398.9 s：
  `210.4 s`，`6.6x`；

结论：NPU 在长音频 + large-v3-turbo 上仍会间歇 `DEVICE_LOST`；回退 CPU 安全但会从零重跑，整体时间约翻倍。

## 3. GPU int8 bug（重要）

### 3.1 现象

- `CL_OUT_OF_HOST_MEMORY`（`clBuildProgram` 错误码 -6）在 GPU 编译阶段出现；
- 不强制 f32 的 int8/默认精度路径在推理时直接 fail-fast：

```
python.exe … 0xc0000409
故障模块：ucrtbase.dll
```

- 分别用应用缓存、全新缓存、**不带 CACHE_DIR** 的独立脚本测试，均崩溃；系统内存充足（31.6 GB，空闲 19 GB），不是系统 OOM。
- **没有冻屏**；崩溃仅限测试进程。

### 3.2 根因判断

- 老版本（v5，未强制 f32）在 11-26 曾完整跑完 int8 GPU（日志 6 个 240 s chunk + SRT 保存）；
- 11-27 为排查 `CL_OUT_OF_HOST_MEMORY` 清理了 `models\openvino\.cache`（约 6.8 GB）以及 48 个 `.cl_cache`；
- 老版本能跑 int8 依赖的是当时机器上已编译好的 OpenCL 内核缓存；删除后 int8 内核需要重新编译，而当前驱动/IGC 状态下重编译会失败/崩溃；
- f32 内核可重新编译并正常运行，所以当前只能稳定使用 f32。

### 3.3 老安装包里的 int8 模型

已解包 v7 安装包（902.5 MB）确认：

- 安装包内含完整 int8 模型，释放到
  `%LOCALAPPDATA%\VideoCaptioner\models\openvino\whisper-large-v3-turbo-int8-ov`（约 789.7 MB）；
- 与笔记本现有模型逐文件 SHA-256 **完全一致**（encoder/decoder/tokenizer/config）；
- 安装包内**没有** fp16 模型，也**没有** `.cl_cache`/`.blob` 缓存。

因此：**从老安装包提取模型无法恢复 int8**；缺的是内核缓存，不是模型。

### 3.4 处理建议

- 核显继续保持 **f32**（应用已强制），不要尝试 int8/无 hint；
- 不要删除 `models\openvino\.cache`（尤其 `.cl_cache`）；
- 如必须尝试 int8：完全关机 -> 清洁重装同版本显卡驱动 `32.0.101.9175` -> 用独立临时缓存 + 60 s 短片测试；仍失败则放弃；
- 稳定优先用 CPU（7.0x）或 f32 核显（7.0x）。

## 4. 其他已验证

- GUI 启动不再探测 QSV，启动日志完整到 `UI startup: shown, entering event loop`；
